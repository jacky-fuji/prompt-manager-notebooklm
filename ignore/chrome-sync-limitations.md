# Chrome Sync (`chrome.storage.sync`) 導入に関する検討記録

**記録日:** 2026年2月23日

プロンプトの複数デバイス間同期機能として `chrome.storage.sync` API の利用を検討したが、現在のAPIの仕様上の制限により、Prompt Manager for NotebookLM への導入は見送られた。
将来的に同期機能の実装を再検討する際のための備忘録として記載する。

## `chrome.storage.sync` の厳格な容量制限

Googleアカウントを通じてデータを同期できる非常に便利なAPIだが、以下の通り厳しいQuota（容量制限）が存在する。

1. **1アイテム（1つのKeyごと）の最大容量: 8,192 bytes (約8KB)**
    * 定数: `chrome.storage.sync.QUOTA_BYTES_PER_ITEM`
2. **全体の最大容量: 102,400 bytes (100KB)**
    * 定数: `chrome.storage.sync.QUOTA_BYTES`
3. **1時間あたりの書き込み回数制限: 1,800回 / 1分あたり: 120回**

## 本拡張機能における課題

現在の Prompt Manager の設計では、すべてのプロンプトデータを `prompts` という単一の配列（1つのKey）として保存している。

* **8KB制限の壁**: 1つのプロンプトにタイトル、テキスト、タグなどのメタデータが含まれるため、日本語の長文プロンプトなどを保存した場合、**わずか数件（合計約2500〜3000文字程度）で1アイテムあたりの制限（8KB）を突破**し、保存エラーとなる。
* **設計変更のコスト**: これを回避するには、プロンプトごとに個別のKey（例: `prompt_001`, `prompt_002`...）に分割して保存し、それらを束ねる「目次」となるインデックス配列を別途用意するなどの複雑なデータ分割・結合ロジックが必要となる。
* **全体100KBの壁**: 仮に分割保存ロジックを実装したとしても、全体で100KBしか保存できないため、ヘビーユーザーが大量の長文プロンプトを保存するには全く足りない可能性がある。

## 現在の結論とアプローチ

長文のプロンプトを多数扱う「Prompt Manager」の性質上、`chrome.storage.sync` への単純な移行は致命的なデータ欠損リスクを伴う。

そのため、大容量（5MB〜無制限）をサポートする現在の `chrome.storage.local` の利用を継続し、データ移行やバックアップ手段としては **「JSONファイルによる手動エクスポート / インポート」機能**で代替することとした（v1.4.0で実装済み）。

今後、デバイス間の自動同期を本気で実装する場合は、Firebase や Supabase などの「外部のBaaS（自前のデータベース）」を用意し、アカウント認証機能とセットで開発する必要がある。
